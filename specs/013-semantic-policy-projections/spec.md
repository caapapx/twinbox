# Feature Specification: 可配置业务语义、分类投影与双向证据

**Created**: 2026-09-18 | **Status**: Draft — 已有部分本地分类/协议实现，完整feature未交付/未发布，本轮仅修订方案
**Input**: 将企业邮件业务事实转成可解释、可重算的分类与事项证据；客户端和平台不硬编码部门业务规则。

## User Scenarios & Testing

### User Story 1 — 换部门不换引擎（Priority: P1）
管理员为交付、商务、运维选择声明式规则；邮箱主人看到同一邮件在不同业务视角下的合理解释，而不是修改客户端代码。
**Independent Test**: 同一组合成邮件、同一引擎，换三个规则包即可重算；非法规则不替换正在使用的版本。
1. Given 审批与周报同时配置，When 审批样本命中，Then 不能因为规则顺序落为周报。
2. Given 多个命中且无法确定主类，When 分类，Then 保留候选与理由并待确认，不伪造确定答案。

### User Story 2 — 按事项、角色和注意力找回证据（Priority: P1）
一封信可以涉及多个事项；多封信可以支撑同一事项。主人可按主类、项目/部门等标签筛选，再看行动/关注/参考视图。
**Independent Test**: 一信多事、多信一事、同主题不同项目，以及旧时间窗材料均能定位；缺覆盖显示未知。
1. Given To 仅知会而 CC 明确点名，When 生成行动卡，Then 责任由证据决定，不由收件人位置决定。
2. Given 规则更新，When 重算分类，Then 原邮件身份、用户已确认状态和证据来源仍可追溯。

### User Story 3 — 跨系统协作但不越权（Priority: P1）
平台消费有界证据，并把人工纠正或执行回执交回 TwinBox；主人能区分建议、确认和源系统事实。
**Independent Test**: 授权纠正成功，重复无副作用，旧版本冲突可见；未授权反馈及正文夹带均拒绝。

### Edge Cases
- 无规则、无正文证据、历史未覆盖、未知分类、同一邮件多业务含义。
- 两账户相同 Message-ID、同信多文件夹、UIDVALIDITY 变化和重抓；不据此跨账户合并。
- 乱序反馈、权限撤回、重算中崩溃、读取旧快照、发布失败。
- 源材料中的状态/数字与当前事实冲突；外部执行成功但业务未验收。

## Requirements

### Functional Requirements
- **FR-001**: 分类必须由可版本化的声明式业务规则定义，业务实体和部门规则不得写入核心或客户端；非法/越权规则拒绝发布并保留旧版本。
- **FR-002**: 支持每事项一个可选主事件类别及多维、多值标签；展示标签目录与解释。邮件兼容摘要不替代事项级结果；冲突、无覆盖、低证据分别可识别。
- **FR-003**: 保留行动/关注/参考作为注意力视图，紧急度、可行动性、兴趣、敏感度等作为派生轴；它们不是邮件物理归档，也不是授权依据。
- **FR-004**: 明确区分源邮件、线程、事项与证据观察，允许一信多事、多信一事；不以主题或收件人角色直接断言归属/责任。
- **FR-005**: 每项推断保存规则版本、证据引用、观察时间、覆盖窗口及理由；来源报告值与当前业务真值分开，引用须属于有权访问的输入。
- **FR-006**: 分类结果独立于短期简报可持久读取和重算；提供覆盖/过期/未知状态，权限撤回和删除可失效，不把未知当作不匹配。
- **FR-007**: 客户端和下游按动态目录及不透明分类值消费；新增业务类别无需平台枚举迁移；旧消费者通过兼容期继续工作。
- **FR-008**: 向平台仅输出按授权裁剪的引用和有界元数据；拒绝全文、附件、凭据及嵌套伪装；来源权限由可信绑定决定。
- **FR-009**: 接收有身份、有依据的纠正提议、人工确认及外部执行回执，具备幂等、版本冲突和拒绝原因；回执不自动等于邮件操作或业务完成。
- **FR-010**: 规则发布、数据纠正、数据可见性、执行授权彼此独立；聊天反馈不能发布全局规则，默认不产生邮箱副作用。
- **FR-011**: 保持原有恢复、增量消费、投影发布、新鲜度和读取路径承诺；关闭新能力或回滚后旧读路径仍可用。
- **FR-012**: 用匿名规则样例、固定业务案例、越权负例和配对人工基线验证；未确认的金标或未实测的收益必须明确标注。

### Key Entities
- **业务规则包**：组织提供的声明式类别、条件、标签和解释；与访问控制规则分离。
- **邮件引用 / 事项 / 证据观察**：分别承载来源定位、业务事项身份和带时间的观察。
- **分类结果 / 覆盖记录**：规则版本下的派生结果及可用范围；支持失效与重算。
- **纠正决定 / 外部回执**：有演员身份和预期版本的业务数据反馈，不是配置发布命令。

## Success Criteria
- **SC-001**: 三个匿名业务规则包通过同一组接口工作；审批误分回归、一信多事和同主题不同项目用例全部通过。
- **SC-002**: 安全负例中越权读取、全文泄漏、隐式邮箱操作、重复副作用均为零；无证据责任断言必须降级。
- **SC-003**: 固定业务案例逐例报告分类、证据、人工纠正和失败原因；新结果不劣于冻结基线，关键安全案例必须全通过。
- **SC-004**: 配对试点至少覆盖三类事件且每类三次同口径任务，报告人工时间、纠错次数、运行成本和不确定性；无实测不宣称ROI成立。

## Assumptions
- 先支持账户绑定的一个有效业务规则包；部门/个人配置先显式选择，自动多层继承不在本版承诺中。
- 安全默认值为只读、最小权限、未确认不执行；真实规则启用与现场试点须管理员另行确认。
- 历史材料用于候选评测，未经业务负责人确认不当作验收金标。

## Platform independence — 2026-09-18 clarification

TwinBox是工具与数据载体，本feature属于其自身能力，不是AgentOS通用控制面建设或跨场景业务验证的强制前置。真实业务证据可用于判断是否值得建设长期接入，但不能将邮件类别/身份/协议推广成运维、会议等专业Agent的强制模型。各领域能力仍归专业团队；本次不改变既有功能/安全验收要求，也不授权真实数据写入。
